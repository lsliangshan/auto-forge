# AutoForge 业务角色与用户管理设计规格

日期：2026-08-21

状态：已完成需求确认，等待书面规格复核

## 1. 目标

为 AutoForge 增加应用层业务角色。CloudBase PostgreSQL 是角色的唯一权威来源，本地 SQLite 保存已登录用户的角色投影。首期支持普通用户和超级管理员；超级管理员可以查看 CloudBase 用户目录并修改其他用户的业务角色。

角色必须进入注册、登录、启动恢复和窗口聚焦刷新链路。用户管理入口只向具有 `manage_users` 能力的会话展示，但 Renderer 状态不作为最终授权依据；所有管理操作由 CloudBase 云函数和 PostgreSQL 事务函数重新鉴权。

## 2. 已确认范围

### 2.1 包含

- 当前可分配角色：`user`、`super_admin`。
- 当前业务能力：`manage_users`。
- CloudBase PG 角色表、不可变角色审计表、索引、约束和事务函数。
- 一个最小职责的 CloudBase 角色管理云函数。
- 一次性存量用户回填和首位超级管理员初始化脚本。
- 本地 SQLite `local_user_roles` 表及会话投影。
- 注册默认角色、登录取角色、启动恢复、窗口聚焦刷新和失败关闭。
- 仅超级管理员可见的用户管理菜单与 `/users` 页面。
- 用户列表分页、指定字段搜索、脱敏展示和单用户角色修改。
- 角色变更的并发控制、幂等、防自修改、防最后管理员降级和审计。

### 2.2 不包含

- 动态角色定义页面、角色定义表、权限表或多角色关系。
- 新增用户、删除用户、封禁/解封用户、重置密码、修改邮箱或手机号。
- 批量修改角色、导出用户、展示角色审计记录。
- 超级管理员读取其他用户的聊天、工作流、执行记录、设置或其他业务数据。
- 超级管理员读取其他用户的大模型用量与消费。
- 将本机 `chat_runs` 或 `provider_usage_events` 上传 CloudBase。
- 修改现有设置页“用量与消费”的数据来源或行为。
- 未经单独复核直接修改当前 CloudBase 环境。

## 3. 当前系统事实

- 当前 CloudBase 环境为 PostgreSQL 模式，环境 ID 在现有认证适配器中固定为规范完整 ID。
- CloudBase 身份会话是认证依据；本地 `local_auth_session` 不是权限证明。
- 当前登录、注册和恢复会话会把 CloudBase 用户投影到 `local_users`、`local_user_profiles` 和 `local_auth_session`。
- 本地用户库只包含在本机出现过的用户，不能作为全局用户目录。
- 当前“用量与消费”只统计本机当前保留的模型调用记录，并按当前登录 UID 查询。
- 项目当前没有角色管理云函数或 CloudBase 业务数据库访问模块。

## 4. 方案选择

### 4.1 采用：CloudBase 主数据 + SQLite 投影

CloudBase PG 保存权威角色，SQLite 只缓存本机出现过的身份角色。登录、注册和恢复会话必须先取得云端角色，再完成本地四表事务，最后才把完整会话返回 Renderer。

### 4.2 采用：薄云函数 + PostgreSQL 事务函数

云函数负责解析请求、从受信请求上下文取得调用者 UID、调用数据库函数、脱敏输出和映射稳定错误。行锁、乐观版本、防锁死、角色写入和审计写入由 PostgreSQL 函数在单个事务内完成。

### 4.3 未采用的方案

- **客户端直连角色表**：扩大攻击面，客户端可尝试伪造角色写入。
- **CloudBase 与 SQLite 双主**：产生冲突合并和跨设备不一致。
- **仅隐藏菜单**：直接路由、IPC 或云函数仍可能被绕过。
- **现在建设完整动态 RBAC**：首期只有两个真实角色和一个能力，角色目录与权限表没有实际调用方。
- **在 `auth.users` 上添加注册触发器**：官方未明确承诺可安全修改该系统认证表。
- **在读取用户列表时隐式写角色**：读操作不应产生难以预期的角色审计。

## 5. 角色与能力模型

### 5.1 当前映射

| 角色 | 中文显示 | 能力 |
|---|---|---|
| `user` | 普通用户 | 无管理能力 |
| `super_admin` | 超级管理员 | `manage_users` |

首期所有管理界面按能力判断，不在组件中散落 `role === 'super_admin'`。

### 5.2 向前兼容

- 角色标识使用受限字符串，格式为 `^[a-z][a-z0-9_]{0,63}$`。
- 当前“可分配角色”输入仍严格限制为 `user | super_admin`。
- CloudBase 角色表首期使用可迁移的文本 `CHECK`，不使用 PostgreSQL ENUM。
- SQLite 不把角色限制为两值，只校验角色标识格式，避免旧客户端遇到未来新角色时无法落库。
- 授权快照返回 `role` 与 `capabilities`；未知角色和未知能力默认不授予权限。
- 旧客户端看到未知角色时显示只读“未知角色（role_id）”，禁止修改并提示升级。
- 后期新增角色时，先发布服务端能力映射和客户端显示支持，再迁移云端约束并开放分配。

## 6. 数据模型

### 6.1 CloudBase PG：`public.app_user_roles`

```text
user_id       varchar(64) primary key
role          varchar(64) not null
version       bigint not null default 1
created_at    timestamptz not null default now()
updated_at    timestamptz not null default now()
updated_by    varchar(64) null
```

约束：

- `user_id REFERENCES auth.users(id) ON DELETE CASCADE`。
- `role` 首期限制为 `user` 或 `super_admin`。
- `version >= 1`。
- `updated_by = null` 表示初始化或回填等系统操作；不建立外键。

### 6.2 CloudBase PG：`public.app_user_role_audit`

```text
id                bigint generated by default as identity primary key
request_id        varchar(128) unique not null
target_user_id    varchar(64) not null
old_role          varchar(64) null
new_role          varchar(64) not null
operator_user_id  varchar(64) null
source            varchar(32) not null
expected_version  bigint null
result_version    bigint not null
created_at        timestamptz not null default now()
```

审计表不引用 `auth.users`，确保身份用户被删除后历史仍保留。表只允许服务端插入，不允许应用更新或删除。`source` 区分自助补建、存量回填、首位管理员初始化和管理员修改。

### 6.3 本地 SQLite：`local_user_roles`

```text
user_id           text primary key
role              text not null
version           integer not null
cloud_updated_at  integer not null
synced_at         integer not null
```

约束：

- `user_id REFERENCES local_users(id) ON DELETE CASCADE`。
- `role` 只验证受限标识格式，不固定为当前两种角色。
- `version >= 0`；正式云端记录从 1 开始，0 只用于云端列表中“尚未落表的默认角色”，不得作为已同步本地角色保存。
- 本地不保存 `updated_by`、能力映射和审计记录。

## 7. 数据库权限与事务函数

### 7.1 表权限

- 两张业务表启用 RLS。
- 不给 `anon`、`authenticated` 或 `PUBLIC` 授予直接读写权限，也不创建客户端读写 Policy。
- 数据库事务函数撤销 `PUBLIC`、`anon`、`authenticated` 的执行权限，仅允许服务端角色调用。
- API Key/service-role 凭证只存在于云函数服务端环境，不进入 Electron、SQLite、日志或仓库。

### 7.2 事务职责

数据库函数至少提供三类内部能力：

1. 确保当前身份具有角色记录，缺失时创建 `user` 并写审计。
2. 分页查询 `auth.users`，左连接角色表，规范化用户状态并脱敏联系方式。
3. 修改单个用户角色，在一个事务中完成：
   - 锁定目标角色行和必要的管理员计数范围；
   - 验证目标身份存在、非匿名；
   - 验证调用者拥有 `manage_users`；
   - 拒绝修改调用者自己的角色；
   - 验证 `expected_version`；
   - 防止可登录的最后一个 `super_admin` 被降级；
   - 更新或以版本 1 插入角色；
   - 写入不可变审计。

同一 `request_id` 与相同参数重试时返回原始审计结果；同一 ID 搭配不同参数时返回冲突。即使目标用户后来再次被修改，旧请求也不能把角色改回去。

## 8. 云函数契约

云函数只暴露以下三个业务动作，不提供通用 SQL 或任意动作转发。

### 8.1 `ensureMyRole()`

输入不接受调用者 UID。调用者身份只取 CloudBase 请求上下文。

返回：

```ts
interface AuthorizationSnapshot {
  role: string
  capabilities: string[]
  version: number
  updatedAt: string
}

interface EnsureMyRoleResult extends AuthorizationSnapshot {
  userId: string
}
```

共享 `AuthUser` 的 `authorization` 字段使用 `AuthorizationSnapshot`；云函数结果额外返回服务端从请求上下文解析出的 `userId`，供 Main 校验结果确实属于当前身份。

### 8.2 `listUsers(input)`

```ts
interface ListUsersInput {
  page: number
  pageSize: 20 | 50 | 100
  filter?: {
    field: 'username' | 'displayName' | 'userId' | 'email' | 'phone'
    value: string
  }
}
```

- 仅 `manage_users`。
- 默认按用户创建时间倒序、UID 稳定排序。
- 返回 `items`、`page`、`pageSize`、`total`。
- 邮箱和手机号只返回脱敏值；UID、用户名和昵称可完整返回。
- UID、邮箱和手机号使用精确匹配；用户名和昵称遵循真实 PG 字段支持的匹配语义，不在客户端全量拉取后伪造模糊搜索。
- 匿名用户排除；封禁用户保留并显示状态。
- 缺少角色记录的正式用户显示为 `user`、`version = 0`，读取时不写数据库。
- PG 同库 SQL 直接查询 `auth.users` 是首选路径；实施前必须读取真实表结构。只有真实环境无法提供所需字段时才退回官方用户管理 API。

### 8.3 `updateUserRole(input)`

```ts
interface UpdateUserRoleInput {
  requestId: string
  targetUserId: string
  newRole: 'user' | 'super_admin'
  expectedVersion: number
}
```

仅 `manage_users`。返回目标用户 UID、最新角色、能力、版本和更新时间。

### 8.4 稳定错误码

```text
AUTH_REQUIRED
FORBIDDEN
USER_NOT_FOUND
INVALID_INPUT
ROLE_CONFLICT
SELF_ROLE_CHANGE_FORBIDDEN
LAST_SUPER_ADMIN
REQUEST_ID_CONFLICT
SERVICE_UNAVAILABLE
INTERNAL_ERROR
```

空列表返回 `items: []`，不是错误。SQL、堆栈、服务端凭证、完整联系方式和 Provider 原始错误不得返回 Renderer 或写入普通日志。

## 9. 认证与同步数据流

### 9.1 注册、登录和启动恢复

1. `CloudBaseAuthService` 完成身份认证或恢复真实 CloudBase 会话。
2. Application 认证门面调用角色服务 `ensureMyRole()`。
3. 角色服务返回授权快照；注册用户缺失角色时云端创建默认 `user`。
4. 本地会话投影事务一次写入 `local_users`、`local_user_profiles`、`local_user_roles`、`local_auth_session`。
5. 四表提交成功后，返回包含必填 `authorization` 的 `AuthSession`。
6. Renderer 才能进入工作台。

CloudBase 身份已创建但角色补建失败时，不尝试危险的账号删除回滚。登录失败并清理本地认证状态；下次登录重新补建。

### 9.2 窗口聚焦刷新

- 重新调用 `ensureMyRole()` 并覆盖本地角色投影。
- 刷新成功后更新授权能力和菜单。
- 刷新失败时保留身份会话与普通功能，但把授权状态标记为未确认，隐藏用户管理菜单并禁止进入 `/users`。
- 缓存中的旧 `super_admin` 不得继续提供管理能力。

### 9.3 管理员修改其他用户角色

1. Main 生成稳定 `requestId`，调用云函数。
2. 云端事务成功后，角色修改即成功。
3. 如果目标用户在本机已有本地用户和角色投影，尝试更新缓存；没有本地用户时不创建额外投影。
4. 本地缓存失败不回滚云端，界面显示非阻断提示，下次登录或刷新修复。

## 10. 模块边界

- `CloudBaseAuthService`：身份登录、注册、令牌与用户资料，不访问 SQLite 或角色表。
- `CloudBaseUserRolePort/Service`：调用云函数，解析角色、用户列表和角色更新结果。
- Application 认证门面：编排身份认证、角色获取和本地四表投影。
- 本地会话投影 Repository：负责四表原子同步。
- 本地角色 Repository：负责聚焦刷新和管理员修改后的缓存操作。
- `UserAdminService`：Main 中受保护的用户管理业务接口。
- IPC/Preload：严格校验用户管理输入输出，不接受调用者角色或 UID。
- Renderer Auth Store：保存授权快照和授权新鲜度。
- Renderer User Admin Store/View：列表、搜索、分页、角色确认和错误状态。
- 共享包：集中定义角色标识、可分配角色、能力、DTO、Schema 与稳定错误码。
- CloudBase 角色云函数：外部安全边界和响应脱敏。
- PostgreSQL 事务函数：角色一致性和审计的最终数据边界。

## 11. UI 与路由

- App Rail 在“执行记录”和“设置”之间增加“用户管理”。
- 菜单只在授权已确认且包含 `manage_users` 时渲染。
- `/users` 同时要求登录和 `manage_users`。普通用户直接访问时重定向 `/chat` 并显示一次无权提示。
- 角色尚未加载时显示加载态，不提前渲染管理页面。
- 收到 `FORBIDDEN` 时刷新角色并离开用户管理页。

用户管理页面包含：

- 标题、搜索字段选择器、搜索输入、查询、重置和刷新。
- 用户（头像、昵称、用户名）、UID、脱敏联系方式、账号状态、业务角色、创建时间和操作列。
- 当前用户标记，且修改按钮禁用。
- 角色修改确认对话框，明确展示当前角色、新角色和提升/降级影响。
- 页码、每页条数和总数。

未知角色只读。首期不提供新增、删除、封禁、批量、导出和审计入口。

## 12. 安全与隐私

- Renderer 中的角色和能力只用于界面与路由，不作为云端操作授权证明。
- Main 不信任 Renderer 传入的角色、能力或调用者 UID。
- 云函数每次管理操作都读取最新权威角色。
- 角色表和事务函数不开放客户端直接访问。
- 联系方式在服务端脱敏；完整搜索值不得进入日志或 SQLite。
- 普通用户不能修改自己的角色；超级管理员也不能修改自己的角色。
- “最后一个管理员”只统计仍存在、非匿名且可登录的 `super_admin`。
- CloudBase 控制台是应用外管理面；若控制台封禁最后一位管理员，只能通过受控初始化脚本或控制台恢复。
- 服务端凭证通过 CloudBase 环境变量注入并支持轮换，绝不进入 Electron 包。

## 13. 初始化与存量数据

### 13.1 存量回填

- 分页读取全部现有非匿名用户。
- 对缺少记录的用户执行 `insert-if-absent user`。
- 记录新增、已存在和失败数量；存在失败时初始化不算完成。
- 不批量创建本地角色记录。

### 13.2 首位超级管理员

- 标准入口为仓库内受控脚本，显式接收完整 EnvId 和目标 UID。
- 默认支持 dry-run；正式执行需要显式确认参数。
- 校验 UID 存在、非匿名且可登录。
- 调用同一数据库事务边界写角色和审计；重复执行幂等。
- 不猜测第一个注册用户，不把真实 UID 或凭证写入源码和提交记录。
- 控制台手写 SQL 只作为紧急恢复手段。

## 14. 发布与回滚

发布顺序：

1. 只读预检当前环境的 `auth.users`、角色、GRANT、RLS 和可用数据库能力。
2. 经用户复核后创建 PG 表、约束、索引和事务函数。
3. 配置服务端凭证并部署角色云函数。
4. 运行存量回填和首位管理员初始化，核对审计与管理员数量。
5. 使用旧客户端确认现有认证不受影响。
6. 发布包含 SQLite 迁移、角色同步、路由和用户管理页面的新客户端。

回滚遵循“应用可回退、数据不破坏”：客户端或云函数可回退版本；数据库使用向前修复迁移，不自动删除角色表、清空角色或删除审计。

## 15. 测试与成功标准

### 15.1 PostgreSQL

- 表约束、外键级联、RLS/GRANT 默认拒绝。
- 事务函数对未登录、普通用户和超级管理员的授权差异。
- 默认角色、`version = 0` 插入、乐观并发、请求重放和请求 ID 冲突。
- 防自修改、最后可用管理员、封禁状态和审计原子性。

### 15.2 云函数

- 三个动作的严格输入输出 Schema。
- 调用者 UID 只取请求上下文。
- 分页、指定字段搜索、稳定排序、匿名排除和联系方式脱敏。
- 稳定错误映射且不泄漏数据库或凭证信息。

### 15.3 SQLite 与 Main

- 新迁移建立本地角色表且不破坏已有身份数据。
- 注册、验证码登录、密码登录和启动恢复执行四表原子投影。
- 聚焦刷新覆盖角色；失败时保留身份但关闭管理能力。
- 管理员修改后的本地缓存成功、缺失和失败分支。
- IPC 不接受或信任 Renderer 的调用者角色。

### 15.4 Renderer

- 普通用户不显示菜单，直接路由被拦截。
- 超级管理员可以查看分页列表、搜索、刷新和修改其他用户角色。
- 自身按钮禁用、未知角色只读、确认对话框文案正确。
- 冲突刷新、权限失效跳转和本地缓存警告。
- 设置页与“用量与消费”无行为变化。

### 15.5 工程验证

- 相关 Vitest node/component/integration 测试。
- `pnpm typecheck`。
- 改动文件限定 ESLint。
- `pnpm build`。
