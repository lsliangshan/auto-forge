# 添加附件后保留已选模型

## 背景

聊天页选择“视频 / OpenAI: Sora 2 Pro”后，添加图片附件会把模型自动切换为 Alibaba: HappyHorse。用户期望附件添加成功后仍保留明确选择的模型。

## 根因

`ChatComposer.vue` 使用当前附件能力过滤模型选择列表。Sora 2 Pro 的目录能力只声明文本输入，添加图片后它会从过滤结果中消失。随后 `modelIdFor()` 回退到第一个兼容模型，导致界面和发送参数都切换到 HappyHorse。

附件 Store 不会修改模型偏好；问题位于聊天编辑器的展示和交互层。

## 设计

模型选择列表只按当前输出类型筛选，不再因草稿附件变化而移除模型。用户明确选择的模型只要仍支持当前输出类型，就保持选中。

附件兼容性单独用于请求校验：

- 当前模型兼容已添加附件时，保持现有发送行为。
- 当前模型不兼容附件时，保留模型选择，显示“当前模型不支持已添加的附件”，并禁用发送。
- 用户可以手动切换到兼容模型，或移除不兼容附件后继续使用原模型。
- 不修改附件导入流程、模型偏好存储、主进程路由或能力目录解析。

## 数据流

1. 用户选择输出类型和模型，模型 ID 保存到会话生成偏好。
2. 附件导入成功后只更新当前会话的草稿附件。
3. 编辑器继续从会话偏好解析已选模型，不根据附件选择其他模型。
4. 编辑器依据已选模型的输入能力检查草稿附件。
5. 不兼容时阻止提交；兼容后使用原有模型 ID 和生成参数发送。

## 测试

在 `apps/desktop/tests/components/chat.test.ts` 增加组件级回归测试：

1. 初始化视频输出，已选 Sora 2 Pro，同时提供支持图片输入的 HappyHorse。
2. 验证添加附件前模型为 Sora 2 Pro。
3. 模拟附件成功进入草稿列表。
4. 验证模型仍为 Sora 2 Pro，没有自动切换到 HappyHorse。
5. 验证显示不兼容提示且发送按钮不可用。
6. 验证手动切换到 HappyHorse 后可以正常发送。

先运行该测试并确认它因当前自动回退行为失败，再实施最小修复。随后运行定向组件测试、桌面端类型检查及相关测试回归。

## 影响与风险

改动仅涉及 `ChatComposer.vue` 的模型候选筛选和发送可用性，以及对应组件测试。主要风险是将“支持输出类型”和“支持当前请求”拆开后，旧的无兼容模型提示条件需要保持准确；测试会分别覆盖“没有该输出模型”和“已选模型不支持附件”两种状态。
