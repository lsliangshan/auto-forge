# AutoForge 工作流发布、审核与分发设计规格

日期：2026-08-21
状态：待书面复核

## 1. 背景与目标

AutoForge 当前支持在桌面应用中创建、编辑、校验、构建、调试和本地安装 TypeScript 工作流，但没有远程提交、人工审核、正式发布或工作流大厅。现有本地安装能力只解决单设备使用，不能证明一个工作流经过平台审核，也不能安全地把同一份产物分发给其他用户。

本设计新增完整的最小发布闭环：开发者完成本地开发与调试后提交不可变源码快照；CloudBase 服务端在隔离环境中重新构建并执行自动安全检查；超级管理员审核源码、依赖、权限和检查结果；审核通过后由服务端签名并发布；普通登录用户可以从工作流大厅下载、验签、安装、升级和使用正式版本。审核不通过时，开发者能看到结构化原因，修改后重新提交。

本设计以平台分发为边界，不取消本地优先能力。未审核工作流仍可在开发模式中本地构建、调试和安装，但不得进入远程大厅，也不得伪装成正式发布版本。

## 2. 已确认的现状

- 桌面端使用 Electron、Vue 3、Pinia、Element Plus、Zod、TypeScript、esbuild 和本地 SQLite。
- CloudBase 身份认证已经接入 Electron Main；CloudBase UID 是登录用户的权威身份。
- 渲染进程通过类型化 Preload/IPC 使用 Main 服务，不直接持有 CloudBase Token 或本地文件系统能力。
- 本地工作流以 `workflow.json` 描述，包含 `id`、`version`、权限、输入输出 Schema、入口文件和代码哈希。
- 本地构建使用 esbuild，当前目标是 `platform: browser`、`format: esm`，并把 `@autoforge/workflow-sdk` 保留为唯一运行时外部依赖。
- 工作流运行器在独立进程内使用 `vm.SourceTextModule`，禁止字符串代码生成和 WebAssembly，并拒绝除 Workflow SDK 外的运行时导入。
- 共享契约虽然枚举了浏览器、网络、文件、剪贴板、通知和产物权限，但当前运行协议只完整实现 `browser.open`、`browser.fill`、`browser.click`、`browser.url` 和 `browser.close`。
- 本地安装按 `workflowId + version` 保存 `workflow.json`、编译入口和文件哈希，同一版本不会被覆盖。
- 远程工作流大厅、提交审核和管理员后台在原生产 MVP 中明确未实现；仓库中也没有现成的远程发布 API、CloudBase PostgreSQL Schema 或构建服务可以复用。

因此，本功能是跨桌面端、远程 API、PostgreSQL、私有存储、隔离构建、签名与审核 UI 的新子系统，不是单个按钮或单个页面改动。

## 3. 成功标准

1. 开发者只有在文件已保存、清单有效、本地构建成功且当前快照至少成功调试一次后，才能提交审核。
2. 每次提交形成不可修改的源码快照和独立 `submissionId`，服务端重新构建，客户端产物不作为正式分发来源。
3. 首次有效提交能安全占用全局 `workflowId`；其他用户不能覆盖该 ID 或提交其后续版本。
4. 超级管理员可以查看完整源码、相对上一发布版本的差异、依赖树、权限变化、自动检查结果和本地调试证明。
5. 管理员可以通过、驳回或在临时审核沙箱中运行候选产物；自审被允许但必须二次确认、填写说明并留下独立标记。
6. 驳回后开发者能看到分类、详细说明和审核时间；修改后可用相同的尚未发布版本重新提交。
7. 审核通过后产生服务端签名的正式产物，并在发布完成后自动进入工作流大厅。
8. 普通登录用户只能下载已发布且未撤销、与当前客户端兼容的稳定版本；客户端安装前必须验签并校验全部文件哈希。
9. 新版本必须严格高于历史最高发布版本；升级成功后只启用新版本，旧版本保留用于手动回退，权限授权不跨版本继承。
10. 管理员撤销发布版本后，该版本立即停止新下载；客户端在线同步后自动禁用已安装副本并展示撤销原因。
11. 提交、审核、签名、撤销、策略修改和角色修改都有不可篡改的审计记录。
12. 服务端构建故障、并发提交、并发审核、上传中断和重复请求不会产生重复提交、重复审核或半发布状态。
13. 现有聊天、本地开发、调试、本地安装和工作流执行能力没有回归。

## 4. 范围

### 4.1 本期包含

- CloudBase PostgreSQL 发布领域数据和迁移。
- 基于 CloudBase 会话的发布 API 与服务端角色授权。
- 私有源码、日志、候选产物和正式产物存储。
- 临时上传会话、不可变提交和全局工作流 ID 所有权。
- 受控 npm 依赖安装、隔离构建、安全扫描、许可证与漏洞检查。
- 服务端正式产物签名和客户端验签。
- 开发页“调试 / 发布”检查器页签。
- 桌面端超级管理员审核页面、审核沙箱、发布版本和发布设置。
- 工作流大厅、详情、下载、更新、回退和撤销同步。
- 应用内审核通知、未读状态和离线缓存提示。
- 动态运营配置、审计、数据保留和失败重试。

### 4.2 本期不包含

- 评分、评论、收藏、榜单、推荐算法、付费或分成。
- 匿名浏览、匿名下载、公开 SEO 页面或永久公开下载链接。
- 定时发布、灰度发布、预发布版本或多条长期维护版本线。
- 自动更新工作流；更新必须由用户主动确认。
- 多人协作、工作流所有权转让或开发者认证申请。
- 开发者自行下架、删除已发布版本或篡改历史审核记录。
- npm 私有 Registry、Git/File/HTTP 压缩包依赖、原生扩展或安装脚本。
- 新增网络、文件、剪贴板、通知或产物运行能力。本期只发布现有已完整实现的浏览器类工作流。
- 文件系统访问、绝对路径、本机文件访问或宿主 Node.js 模块直通。

## 5. 核心术语

- **本地项目**：开发者设备上的可编辑源码目录。
- **本地开发版**：未经平台审核，仅能在开发模式中使用的本地构建版本。
- **上传会话**：短期、可过期的私有对象上传授权，不是正式提交。
- **提交（Submission）**：一次不可变的源码、清单、锁文件、调试证明和更新说明快照。
- **检查（Check）**：构建、敏感信息、依赖、漏洞、许可证、能力和动态代码扫描结果。
- **审核（Review）**：超级管理员对一个 `pending_review` 提交作出的不可变结论。
- **发布版本（Release）**：由已通过提交生成、经过服务端签名、可进入大厅的正式版本。
- **撤销（Revocation）**：保留原审核结论但阻止继续分发和运行的安全处置。
- **工作流所有者**：首次有效提交进入待审核后获得该 `workflowId` 的 CloudBase UID。

## 6. 方案选择

### 6.1 采用：CloudBase 统一身份与服务端发布流水线

发布系统继续使用现有 CloudBase 身份，CloudBase PostgreSQL 作为业务真相源，私有云存储保存大文件，CloudRun 承载发布 API、构建处理和内部签名协调。桌面端只通过发布 API 读写远程状态。

最终可下载产物必须由服务端受控构建环境从源码重新生成。客户端构建仅用于本地开发和提交前预检，不作为审核或分发的可信依据。

### 6.2 未采用：客户端直接写数据库和云存储

该方案开发量较小，但无法可靠保护管理员角色、状态流转、限额、ID 所有权、签名和审计，也会把存储授权暴露给桌面端，因此不采用。

### 6.3 未采用：上传客户端编译产物直接发布

管理员审核的源码可能与客户端上传的可执行产物不同，无法建立“所见源码即所运行代码”的保证，因此不采用。

### 6.4 未采用：独立 Web 管理后台

首期审核量和角色规模不需要第二套前端。审核管理直接集成到 AutoForge 桌面应用，服务端授权仍独立执行。后续如果出现专职审核团队，再复用发布 API 建设 Web 后台。

## 7. 总体架构

```text
Desktop Renderer
  ├─ 开发 / 发布 / 审核 / 大厅 UI
  └─ Pinia stores
          │ typed IPC
          ▼
Electron Main
  ├─ 本地项目、构建与调试
  ├─ 源码打包与本地预检
  ├─ CloudBase 会话令牌（仅 Main）
  ├─ Publishing API Client
  └─ 下载、验签、原子安装与撤销同步
          │ HTTPS + CloudBase bearer session
          ▼
Publisher API (CloudRun)
  ├─ 会话验证、角色与所有权
  ├─ 限额、幂等、状态机与审计
  ├─ 上传/下载短期授权
  ├─ 审核与发布编排
  └─ PostgreSQL transaction boundary
      │               │                    │
      ▼               ▼                    ▼
CloudBase PG     Private Storage      Internal Builder
                                          ├─ dependency install
                                          ├─ scans
                                          ├─ deterministic build
                                          └─ candidate artifact
                                                   │ approved only
                                                   ▼
                                             Signing boundary / KMS
```

### 7.1 Renderer 职责

- 只展示公开 DTO 和用户可见状态。
- 收集更新说明、修复说明、审核清单和审核备注。
- 不导入 CloudBase 管理 SDK，不接触 Access Token、Refresh Token、数据库凭证、存储长期凭证或签名私钥。
- 路由和菜单隐藏只改善体验，不作为权限安全边界。

### 7.2 Electron Main 职责

- 读取受控本地项目文件并生成规范化源码归档。
- 计算归档哈希，执行文件数量、体积、路径、禁止文件和敏感信息的本地预检。
- 把当前 CloudBase 会话作为短期 Bearer 身份调用发布 API；Renderer 不获取 Bearer Token。
- 维护本地调试成功证明，并在源码或清单变化时立即失效。
- 下载正式产物、验证签名和文件哈希，再复用现有安装存储的暂存、原子移动和完整性记录模式。
- 同步撤销游标并禁用已撤销版本。

### 7.3 Publisher API 职责

- 作为远程业务唯一入口验证 CloudBase 会话。
- 在 PostgreSQL 事务中执行角色、所有权、限额、ID 预留、版本、活跃提交和状态流转检查。
- 创建短期上传和下载授权，但不把私有存储长期凭证返回客户端。
- 生成构建任务、处理审核结论、创建发布任务、写通知和追加审计事件。
- 不执行不可信构建代码，不持有签名私钥。

### 7.4 Builder 职责

- 使用提交时冻结的源码对象和策略快照工作。
- 在一次性低权限容器中安装依赖、扫描和构建。
- 只写候选产物、构建日志、检查结果和任务状态。
- 不能修改审核结论、发布状态、角色或策略，不能读取其他提交对象，也不能调用签名私钥。

### 7.5 签名边界职责

- 只处理已经存在不可变审核通过记录、候选哈希与发布任务的签名请求。
- 使用腾讯云受控密钥系统中的非导出私钥完成签名。
- 签名调用方必须使用独立服务身份；Builder 无权调用。
- 签名失败只影响发布任务，不回滚管理员已经写入的审核结论。

## 8. 身份、角色与所有权

### 8.1 角色

- 所有已登录用户均为 `user`，可以浏览、下载、开启开发模式和提交自己的工作流。
- `super_admin` 拥有普通用户能力，并可访问审核、撤销和发布设置接口。
- `super_admin` 由 PostgreSQL `user_roles` 记录，以 CloudBase UID 为主键。
- 首个管理员通过受控部署初始化；首期不提供客户端授予或撤销管理员的 UI。
- 角色变更必须记录操作者、旧值、新值、原因和时间。
- 每次敏感请求都读取或短时缓存服务端角色；客户端保存的角色只用于菜单体验，不能授权。

### 8.2 工作流所有权

- `workflowId` 在平台全局唯一，并继续使用现有点分小写标识规则。
- 上传开始只创建短期 ID 预留，不产生所有权。
- 上传完成并创建 `queued` 提交后，预留自动续期到该提交进入 `build_failed` 或 `pending_review`；不能在构建仍活跃时被其他账号抢占。
- 首次提交完成基础校验、依赖安装、构建和自动安全检查并进入 `pending_review` 时，服务端在同一事务中创建 `workflows` 记录并登记所有者。
- 上传中断、项目构建失败或自动检查失败不会永久占用 ID；预留到期释放。
- 人工驳回后所有权继续保留，防止其他账号抢占。
- 只有所有者能提交新版本；超级管理员也不能以审核权限覆盖他人工作流。
- 首期不支持所有权转让、共同所有或同 ID 分叉。

### 8.3 自审

- 超级管理员可以审核自己提交的工作流。
- 自审详情必须显示醒目标记；列表快捷通过不可用于自审。
- 自审通过前必须二次确认并填写审核说明。
- 审计事件设置 `selfReviewed: true`，机器门禁不可跳过。

## 9. 状态模型与不变量

### 9.1 上传会话

上传会话只有 `created`、`uploaded`、`consumed`、`expired` 四种状态。它不是正式提交，不进入审核历史，也不计入活跃提交数。一个上传对象只能被一个提交消费。

### 9.2 提交状态

```text
queued -> building -> pending_review -> approved
                   \                 \-> rejected
                    -> build_failed
```

- `queued`：正式提交已创建，等待 Builder 领取。
- `building`：依赖、扫描或编译正在执行。
- `build_failed`：项目错误或自动门禁失败；快照不可修改。
- `pending_review`：所有自动门禁已通过，等待管理员结论。
- `approved`：审核结论已不可变，等待或已经生成发布版本。
- `rejected`：审核结论已不可变；重新提交创建新的 `submissionId`。

同一 `workflowId` 在 `queued`、`building`、`pending_review` 中最多存在一条活跃提交。`build_failed`、`approved` 和 `rejected` 都是终态。

提交进入 `queued` 后源码、清单、依赖、调试证明和说明全部锁定；开发者不能编辑或撤回该记录。需要修正时必须等待其进入终态，再创建新的提交。

### 9.3 发布状态

```text
publishing -> published -> revoked
```

- 审核通过时在同一数据库事务中写审核结论并创建 `publishing` 发布任务。
- 签名、正式对象写入和索引更新全部成功后变为 `published`。
- `publishing` 不出现在普通用户大厅，平台失败自动重试。
- `revoked` 保留原审核结论、签名、哈希和审计记录，但停止新下载并加入撤销流。
- 撤销版本不能恢复为 `published`；开发者必须使用更高版本重新提交。

### 9.4 版本不变量

- 远程发布只接受 `major.minor.patch` 稳定 SemVer，不接受预发布或构建元数据。
- 驳回或构建失败的版本在未发布前可以重新提交，产生新的 `submissionId` 和 `previousSubmissionId`。
- 一旦 `workflowId + version` 进入 `published` 或 `revoked`，该版本永久占用且不可覆盖。
- 新提交版本必须严格高于历史最高正式版本；发布 `2.0.0` 后不能补发 `1.5.0`。
- 首期不支持并行维护版本线。

## 10. PostgreSQL 数据模型

PostgreSQL 保存业务状态和小型 JSONB 快照；源码、日志和产物正文只保存对象键、长度和哈希。所有时间使用 UTC `timestamptz`，所有 ID 使用服务端生成的 UUID。

### 10.1 核心表

| 表 | 责任与关键字段 |
|---|---|
| `user_roles` | `user_uid` 主键、`role`、创建/更新操作者与时间 |
| `workflows` | `workflow_id` 主键、`owner_uid`、创建时间、当前最高发布版本、当前发布 ID |
| `workflow_id_reservations` | `workflow_id` 唯一、`owner_uid`、`upload_id`、`expires_at` |
| `upload_sessions` | 上传用户、声明 ID/版本、对象键、归档哈希、字节数、状态、过期时间 |
| `workflow_submissions` | 提交 ID、工作流、用户、版本、状态、上次提交、源码对象、源码哈希、更新说明、修复说明、本地调试证明、策略快照、失败归因与时间 |
| `build_jobs` | 提交、尝试次数、平台/项目失败类型、领取租约、下次重试时间、日志对象和候选对象 |
| `submission_checks` | 提交、检查类型、状态、严重级别、机器可读结果和完成时间 |
| `reviews` | 提交唯一、审核人、结论、驳回分类、说明、清单 JSONB、是否自审和审核时间 |
| `workflow_releases` | 提交唯一、工作流与版本唯一、状态、正式产物对象、产物哈希、规范发布清单、签名、签名密钥 ID、发布时间和撤销信息 |
| `review_sandbox_runs` | 提交、审核人、候选哈希、运行终态、开始/结束时间；不保存敏感输入全文 |
| `notifications` | 用户、类型、目标实体、公开载荷、创建和已读时间 |
| `publishing_policy_versions` | 单行版本化策略 JSONB、版本号、修改人、原因和时间 |
| `workflow_categories` | 稳定分类代码、中文名称、排序、启用状态 |
| `rejection_reasons` | 稳定原因代码、中文名称、排序、启用状态 |
| `download_events` | 用户、发布版本、客户端版本和下载时间，不保存工作流运行数据 |
| `audit_events` | 追加写事件、操作者、实体、动作、前后状态摘要、请求 ID 和时间 |

### 10.2 数据库约束

- `workflow_releases(workflow_id, version)` 唯一。
- `reviews(submission_id)` 唯一。
- `workflow_submissions` 使用部分唯一索引，保证每个工作流最多一个 `queued/building/pending_review`。
- 首次提交在所有权正式建立前只通过 `workflow_id` 文本和有效预留关联；进入 `pending_review` 的同一事务创建 `workflows` 后，再建立不可变所有权关系。既有工作流提交必须从创建时就匹配所有者。
- 创建提交时对 `workflowId` 与用户配额使用事务锁；不能依赖先查后写。
- 审核使用 `UPDATE ... WHERE status = 'pending_review'` 的原子条件；第一个成功结论生效，后续并发请求返回冲突。
- 发布、撤销和策略修改都使用乐观版本或状态前置条件。
- `audit_events` 对应用角色只授予 `SELECT/INSERT`，不授予 `UPDATE/DELETE`。
- 大文件删除只清理对象，不删除提交、审核、发布或审计元数据。

## 11. 远程 API 契约

### 11.1 通用规则

- 所有接口使用 `/v1` 前缀和 JSON DTO；二进制正文通过短期私有对象 URL 传输。
- Electron Main 发送 CloudBase Bearer Session；Publisher API 验证会话并从验证结果取得 UID。
- 成功返回 `{ data, requestId }`；失败返回 `{ error: { code, message, details? }, requestId }`。
- `message` 是可展示的稳定中文文案，`code` 用于客户端分支，`details` 不包含 Token、凭证、私有对象键或服务器路径。
- 创建提交、审核结论、撤销和策略修改必须携带 `Idempotency-Key`；相同用户、接口和 Key 的重试返回第一次结果。
- 列表使用不透明游标，不使用可能在并发写入下重复或跳项的页码偏移。

### 11.2 核心公开类型

```ts
type SubmissionStatus =
  | 'queued'
  | 'building'
  | 'build_failed'
  | 'pending_review'
  | 'approved'
  | 'rejected'

type ReleaseStatus = 'publishing' | 'published' | 'revoked'

interface LocalDebugProof {
  buildHash: string
  completedAt: string
  redactedInput: unknown
  outputSummary: string
}

interface ReviewChecklist {
  behaviorMatchesDescription: true
  permissionsAreMinimal: true
  sourceAndDependenciesAreSafe: true
  dependencyRiskAccepted: true
  releaseNotesMatchDiff: true
  automatedChecksPassed: true
}
```

`redactedInput` 在 Main 中按敏感键和敏感值规则脱敏，提交确认框必须展示将上传的内容。任何源码或清单变化都会使 `buildHash` 对应的证明失效。

### 11.3 接口分组

**会话与通知**

- `GET /v1/me/capabilities`：返回公开角色、策略版本和未读通知数。
- `GET /v1/notifications`：读取当前用户通知。
- `POST /v1/notifications/:id/read`：标记单条通知已读。

**开发者发布**

- `POST /v1/uploads`：声明工作流 ID、版本、归档长度和 SHA-256，返回短期上传 URL、必要请求头和过期时间。
- `POST /v1/uploads/:id/complete`：服务端检查对象长度与哈希，转为 `uploaded`。
- `POST /v1/submissions`：消费上传会话，提交更新说明、修复说明和调试证明，返回提交摘要。
- `GET /v1/workflows/:workflowId/submissions`：所有者读取历史提交。
- `GET /v1/submissions/:submissionId`：所有者或超级管理员读取详情。
- `POST /v1/submissions/:submissionId/retry-platform-failure`：只允许重试最终平台异常，不消耗开发者额度。

**审核与管理**

- `GET /v1/reviews`：超级管理员按状态、分类、提交者和时间读取队列或历史。
- `GET /v1/reviews/:submissionId`：读取源码浏览授权、差异、依赖、权限、检查和审核上下文。
- `POST /v1/reviews/:submissionId/sandbox-ticket`：获取绑定候选哈希的一次性审核沙箱票据。
- `POST /v1/reviews/:submissionId/decision`：提交完整清单以及 `approve` 或 `reject` 结论；驳回必须包含启用的分类和详细说明，自审通过必须包含自审说明。
- `POST /v1/releases/:releaseId/revoke`：超级管理员撤销正式版本并填写原因。
- `GET /v1/publishing-policy` 与 `PUT /v1/publishing-policy`：按版本读取和更新运营策略。
- `GET/PUT /v1/workflow-categories`、`GET/PUT /v1/rejection-reasons`：管理启用状态、名称和排序，稳定代码不可复用。

**大厅与下载**

- `GET /v1/marketplace/workflows`：搜索已发布、未撤销且兼容的工作流。
- `GET /v1/marketplace/workflows/:workflowId`：读取发布者、最新版本、权限、兼容性和历史版本摘要。
- `POST /v1/releases/:releaseId/download-ticket`：为当前登录用户生成短期、单版本下载授权。
- `GET /v1/revocations?after=<cursor>`：增量同步撤销版本和新游标。

### 11.4 稳定错误码

至少包含：`AUTH_REQUIRED`、`FORBIDDEN`、`NOT_FOUND`、`INVALID_INPUT`、`CONFLICT`、`RATE_LIMITED`、`WORKFLOW_ID_RESERVED`、`WORKFLOW_OWNERSHIP_CONFLICT`、`ACTIVE_SUBMISSION_EXISTS`、`VERSION_NOT_GREATER`、`VERSION_ALREADY_RELEASED`、`UPLOAD_EXPIRED`、`PACKAGE_POLICY_FAILED`、`BUILD_PROJECT_FAILED`、`BUILD_PLATFORM_FAILED`、`REVIEW_ALREADY_DECIDED`、`RELEASE_NOT_DOWNLOADABLE`、`CLIENT_INCOMPATIBLE` 和 `SIGNATURE_INVALID`。

## 12. 源码包契约

### 12.1 归档内容

Main 生成路径排序、时间戳归零、权限位归一化的规范 ZIP。允许的根内容是：

- `workflow.json`
- `package.json`
- `pnpm-lock.yaml`
- `README.md`、`LICENSE` 或带常见扩展名的许可证文件
- `src/**`
- `assets/**`

`src` 允许 `.ts`、`.tsx`、`.js`、`.mjs` 和 `.json`；`assets` 允许 `.json`、`.txt`、`.md`、`.png`、`.jpg`、`.jpeg` 和 `.webp`。二进制静态资源只能由构建器以内联 Data URL 方式打入单一 bundle，不能在运行时形成任意文件读取能力。

不上传 `node_modules`、`dist`、构建缓存、日志、`.env*`、版本控制目录、压缩包、符号链接、套接字、设备文件或可执行二进制。

`package.json` 不允许发布脚本或安装脚本，只声明精确版本的运行依赖和 `@autoforge/workflow-sdk`。构建工具、TypeScript 和 esbuild 由服务端 Builder 固定提供，不能由工作流项目替换。

### 12.2 限额

- 上传归档不超过 10 MiB。
- 解压后的所有条目总计不超过 10 MiB。
- 单个文件不超过 2 MiB。
- 总条目数不超过 200。
- 禁止嵌套压缩包、重复规范路径、大小写碰撞、绝对路径、反斜线逃逸、`..` 路径段和符号链接。

Main 先检查以提供即时反馈，Publisher API 或 Builder 必须从原始字节独立重做全部检查。

### 12.3 敏感信息

源码、清单、锁文件、调试证明和构建日志都执行敏感键、私钥格式、Token 模式和高熵值扫描。命中阻断规则的项目不能进入人工审核；错误只返回文件与安全行号，不回显完整秘密。管理员没有跳过敏感信息门禁的能力。

### 12.4 现有本地项目兼容

- 新建工作流项目从本功能启用后同时生成最小 `package.json` 和冻结 `pnpm-lock.yaml`。
- 既有项目若只导入相对源码和 Workflow SDK，但缺少依赖文件，发布页提供“生成依赖文件”操作；必须由开发者确认后写入项目，不能在提交时静默修改源码目录。
- 既有项目使用第三方包时，开发者必须先声明精确依赖并生成冻结锁文件；发布页不能根据导入语句猜版本。
- 依赖文件生成或变化属于项目修改，会使既有本地调试成功证明失效，开发者必须重新构建和调试。

## 13. 依赖、构建与自动检查

### 13.1 npm 依赖规则

- 提交必须包含 `package.json` 和 `pnpm-lock.yaml`，并使用 `pnpm@11.15.0` 冻结安装。
- 生产依赖必须是公共 npm Registry 上的精确版本。
- 禁止版本范围、Tag、Git URL、HTTP 压缩包、`file:`、`link:`、workspace、私有 Registry 和认证配置。
- 安装使用冻结锁文件并禁用生命周期脚本。
- 禁止原生扩展、预编译二进制、安装时下载和运行时 `node_modules`。
- 所有第三方依赖必须被服务端构建打入单一 ESM bundle；无法静态打包的依赖导致项目失败。

### 13.2 许可证规则

自动允许：MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、0BSD。

未声明、无法识别、自定义、多许可证表达不清或 GPL、AGPL、LGPL、SSPL 等不在白名单内的许可证会阻止进入人工审核。管理员不能手动跳过许可证门禁。

### 13.3 漏洞规则

- Critical、High：阻止进入人工审核。
- Moderate：允许审核，但必须醒目标记；审核清单中的依赖风险确认表示管理员知晓该具体快照的风险。
- Low：记录并展示，不阻止。
- 漏洞情报不可用时标记平台检查失败并自动重试，不能默认放行。
- 漏洞、恶意包情报和撤销名单结果有效期为 24 小时；管理员通过前结果过期时自动复扫，复扫不消耗开发者额度。
- 已发布版本后来出现 High/Critical 风险时产生安全告警，由超级管理员决定是否撤销。

### 13.4 Node.js 兼容层

本期允许的内置模块只有：

- `node:buffer`
- `node:url`
- `node:util`
- `node:crypto` 的哈希、安全随机值和恒定时间比较子集

这些模块在构建时解析到平台维护的纯沙箱兼容实现，不链接宿主 Node。最终 bundle 仍只能把 `@autoforge/workflow-sdk` 作为运行时外部导入。兼容层版本写入发布清单和兼容性判断。

`fs`、`fs/promises`、`child_process`、`cluster`、`net`、`http`、`https`、`http2`、`dns`、`dgram`、`tls`、`worker_threads`、`vm`、`module`、`repl`、`process` 以及任何未明确列入白名单的内置模块都被拒绝。

### 13.5 动态代码规则

源码、依赖与最终 bundle 不得包含 `eval`、`new Function`、WebAssembly、动态 `require`、无法静态确定目标的 `import()` 或从字符串、网络、本地数据加载代码的路径。该门禁不可由管理员跳过。

### 13.6 能力规则

正式发布清单只允许 `browser.open`、`browser.fill`、`browser.click`、`browser.url` 和 `browser.close`。声明其他共享契约中尚未实现的权限会阻止提交进入审核。npm 包只能执行纯计算，不能绕过 Workflow SDK 直接访问网络、文件、系统命令或宿主环境。

### 13.7 构建资源

默认单次构建最多 5 分钟、2 vCPU、1 GiB 内存和 1 GiB 临时磁盘。容器使用只读基础文件系统、无特权模式、无 CloudBase 管理凭证、无签名私钥和无用户 Token；任务结束后销毁。

只有依赖获取阶段可以访问受控 npm Registry 代理；扫描和编译阶段禁止外网。资源数值可以在服务端安全上下限内动态调整，但容器隔离、凭证禁令和网络阶段隔离不可关闭。

### 13.8 本地调试门禁

- 当前源码和清单生成的 `buildHash` 必须至少对应一次 `completed` 调试执行。
- 取消、失败、等待权限或仍在运行的执行不算通过。
- 任何源码或清单变化立即使证明失效。
- 提交附带完成时间、脱敏输入和输出摘要；该证明是开发者预检记录，不是服务端可信安全证明。

## 14. 失败归因与重试

- **项目失败**：依赖、编译、策略或安全检查不通过。提交进入 `build_failed`；开发者修改后重新提交，并消耗每日构建额度。
- **平台失败**：构建节点、存储、内部网络或平台服务异常。系统自动重试最多 3 次，提交保持活跃，不要求重新上传，不额外消耗额度。
- 三次平台重试仍失败时显示“平台构建异常”，允许开发者触发不计额度的重试，并产生运维告警。
- Builder 使用领取租约和任务尝试号；过期租约可被其他实例接管，旧实例不能覆盖较新的终态。
- 审核通过后签名或正式对象写入失败时，提交保持 `approved`，发布保持 `publishing` 并自动重试，不重复审核。

## 15. 审核机制

### 15.1 审核材料

审核详情必须展示：

- 提交人、工作流所有者、服务端发布者资料和清单署名差异。
- 版本、更新说明、修复说明、提交时间和源码哈希。
- 完整源码和相对上一发布版本的源码差异。
- 清单、输入输出 Schema、激活示例和权限差异。
- 直接与传递依赖树、版本变化、许可证和漏洞结果。
- 服务端构建日志、产物哈希、构建环境与兼容层版本。
- 本地调试证明和可选审核沙箱记录。

### 15.2 通过清单

管理员通过前必须逐项确认：

1. 功能行为与名称、描述和输入输出契约一致。
2. 权限范围遵循最小权限原则。
3. 源码和依赖未发现恶意行为或敏感信息。
4. npm 依赖用途合理，自动风险结果已知并接受。
5. 版本更新说明与实际差异一致。
6. 自动构建、签名准备和兼容性检查均通过。

清单作为审核记录保存，不能替代源码判断，也不能改变机器门禁结论。

### 15.3 驳回

驳回必须选择启用的原因代码并填写详细说明。默认原因是：构建或运行异常、权限申请不合理、存在安全风险、功能或描述不一致、内容违规、重复或冒用工作流、其他。

开发者重新提交被驳回工作流时必须填写本次修改说明，并通过 `previousSubmissionId` 关联上一轮。

### 15.4 并发审核

首期不领取、不长期锁单。多个管理员可同时查看；第一个成功把状态从 `pending_review` 原子更新为终态的请求生效，后续请求返回 `REVIEW_ALREADY_DECIDED` 并刷新最终结论。

### 15.5 审核沙箱

- 管理员可下载绑定候选哈希的一次性沙箱票据，在本机临时运行服务端候选产物。
- 候选不进入已安装列表，不能被聊天自动召回。
- 所有权限仍按普通工作流规则请求，管理员身份不绕过用户授权。
- 测试结束后删除临时产物和临时授权。
- 是否执行、终态和时间写入审核记录；人工试运行不是强制通过条件。

## 16. 发布、签名与分发

### 16.1 正式产物

正式包只包含：

- `workflow.json`
- `dist/index.js`
- `release.json`
- `release.sig`

`release.json` 使用固定 JSON Canonicalization 规则，包含工作流 ID、版本、发布者 UID、正式文件 SHA-256、权限、`sdkVersion`、`minAppVersion`、构建器版本、Node 兼容层版本、发布时间、签名算法和 `signingKeyId`。

名称、描述、平台分类、署名、权限、输入输出 Schema、激活示例、更新说明和兼容性都属于发布快照。版本进入 `publishing` 后这些字段不能单独编辑；任何用户可见元数据变化都必须使用更高版本重新审核。只有发布状态、撤销原因、下载统计和平台展示配置可以独立变化。

### 16.2 签名

- 使用云端非导出密钥和 `RSASSA-PSS-SHA256` 对规范 `release.json` 签名。
- 客户端内置带 ID 的可信公钥集合，先验签再校验每个文件哈希。
- 密钥轮换通过新增 `signingKeyId` 和随 AutoForge 应用发布更新的可信公钥集合完成；旧公钥在其发布版本仍受支持时保留。
- 验签失败、未知密钥、文件哈希不一致、身份不匹配或版本不兼容时拒绝安装。

### 16.3 大厅与下载

- 大厅只显示 `published`、未撤销且与当前客户端兼容的工作流。
- 每个 `workflowId` 展示一个条目，默认版本是最高已发布稳定 SemVer。
- 详情展示发布者、清单署名、最新版本、更新时间、分类、权限和更新说明。
- 首期详情可以展示历史发布摘要，但只允许普通用户安装最新版。
- 下载 URL 短时有效并绑定单一发布版本；服务端记录用户、发布版本、客户端版本和时间，不记录工作流输入输出。

### 16.4 安装、更新与回退

- 下载到本地暂存目录后先验签、校验哈希和兼容性，再原子移动到正式安装目录。
- 新版本安装失败时不改变旧版本启用状态。
- 新版本安装成功后自动启用新版本，并禁用同一工作流的其他已安装版本。
- 旧版本保留在本地，用户可以手动回退；任何时刻同一工作流最多启用一个版本。
- 权限授权按 `workflowId + version` 隔离，新版本首次运行重新请求权限。
- 新版本不会自动下载或自动覆盖；客户端只提示可用更新，由用户确认。
- 正式版和本地开发版使用不同来源身份。若下载的正式版与本地开发版 `workflowId + version` 相同，安装器不能覆盖开发目录或静默替换来源；用户必须先移除对应本地安装副本或提升本地版本，开发项目源码本身始终保留。

### 16.5 撤销

- 超级管理员必须填写撤销原因。
- 撤销立即停止新下载并从最新版索引移除。
- 客户端在启动、恢复网络和周期同步时按游标拉取撤销流。
- 同步到撤销后自动禁用对应版本，保留本地文件用于取证或等待修复，用户不能重新启用。
- 完全离线设备无法即时获知远程撤销；这是离线运行的明确边界。

## 17. 兼容性

- `sdkVersion` 是服务端构建使用的 Workflow SDK 精确版本。
- `minAppVersion` 是允许安装的最低 AutoForge 稳定版本。
- 发布清单记录构建目标运行时和 Node 兼容层版本。
- 大厅按当前客户端过滤或标记不兼容工作流；不兼容版本不能获取下载票据。
- 应用升级后若已安装工作流失去兼容性，客户端禁用并解释原因，不静默尝试运行。
- 首期不声明最高客户端版本。

## 18. 动态配置

### 18.1 默认运营策略

- 每个账号最多 5 个活跃提交。
- 每个账号每天最多发起 50 次服务端项目构建。
- 同一工作流项目失败后默认冷却 1 分钟。
- 单次构建默认 5 分钟、2 vCPU、1 GiB 内存和 1 GiB 临时磁盘。
- 上传、解压、单文件和条目限额使用第 12.2 节数值。
- 人工驳回源码和日志保留 180 天；构建失败或上传中断对象保留 30 天。

### 18.2 可动态配置

- 提交与构建限额、失败冷却。
- 上传和构建资源数值，受服务端硬编码安全上下限约束。
- 工作流分类、驳回原因、审核提醒和列表排序。
- 非正式对象保留期限。

配置修改后影响新请求，不中断已开始的上传、构建或审核。每次修改记录旧值、新值、修改人、原因和策略版本。服务端可以短时缓存，但配置更新后必须主动失效缓存。

### 18.3 不可动态关闭的安全不变量

- 路径、符号链接、本机文件和敏感信息防护。
- Node 白名单、动态代码和能力门禁。
- 服务端鉴权、所有权、不可变快照和状态机。
- 人工审核、正式签名、客户端验签和文件哈希。
- 已发布版本不可覆盖、审计事件不可修改。

这些规则只能通过代码评审和受控部署改变。

## 19. 分类与发布者身份

### 19.1 默认分类

默认启用：浏览器自动化、信息检索、数据采集、数据处理与分析、内容创作、办公协作、开发工具、营销运营、电商、客户服务、教育学习、生活服务、其他。

发布版本只能选择一个主分类。分类可动态停用或调整显示名和排序；稳定分类代码不可复用。已发布版本保存分类快照，后续配置变化不篡改历史发布元数据。

### 19.2 发布者与署名

- 可信发布者来自 `workflows.owner_uid` 对应的 CloudBase 用户资料投影。
- `workflow.json.author` 只作为作品署名文本，不参与权限或可信认证。
- 署名与发布者不同时，详情页同时展示。
- 管理员身份不会自动给其工作流增加“官方”标识；首期没有官方认证体系。

## 20. UI 设计规格

### 20.1 Purpose Statement

发布界面要让开发者清楚知道“为什么现在不能提交、提交后处于哪一步、被驳回后要改什么”；审核界面要让超级管理员在不丢失代码上下文的情况下判断来源、差异、依赖和权限风险；大厅要让普通用户在下载前理解发布者、能力范围和兼容性。所有界面都服务于可追踪和可验证，不营造“上传即发布”的错觉。

### 20.2 Aesthetic Direction

采用现有 AutoForge 的 **Industrial / Utilitarian（工业化工具台）** 方向：密度适中的表格、清晰的状态点、单色代码区、克制的警告色和明确的分栏。发布功能延续既有工作台，不增加营销式大卡片、装饰背景或新的视觉概念。

### 20.3 Color Palette

- 画布 `#f3f5f8`
- 主表面 `#ffffff`
- 石墨文字与导航 `#20242b`
- 主要操作钴蓝 `#2563eb`
- 成功 `#15803d`
- 警告 `#b45309`
- 危险 `#b42318`

暗色模式继续使用现有 `--af-*` 对应 Token。状态不能只靠颜色，必须同时显示文字或图标。

### 20.4 Typography

继续使用项目现有字体栈 `Inter, ui-sans-serif, -apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", sans-serif`，代码与 ID 使用现有等宽字体栈。这里明确覆盖通用 UI 技能对 Inter 和系统字体的默认限制，因为仓库已有批准并全局使用的品牌排版系统；本功能不借机修改全局字体或引入远程字体。

### 20.5 Layout Strategy

保留 52px 主导航、240px 上下文侧栏、中央工作区和可折叠右检查器的非对称工作台结构。发布状态放进开发检查器，审核详情把代码差异作为中央主内容、把结论清单放在右侧决策栏；大厅继续使用高信息密度列表和详情检查器。这里同样覆盖通用 UI 技能要求重新“打破网格”的默认规则，因为现有多栏工作台本身就是产品的既定空间结构。

### 20.6 开发页

- 右侧检查器标题下增加“调试 / 发布”分段页签。
- “调试”保留现有校验、构建、权限和运行内容。
- “发布”按顺序展示：当前远程状态、就绪清单、更新说明、必要的修复说明、提交按钮、最新审核结果、历史提交。
- 就绪清单逐项显示文件已保存、清单有效、构建成功、当前 Hash 调试成功、版本可用、无活跃提交和更新说明已填写。
- 提交确认框展示版本、权限、源码上传范围、脱敏调试输入和“审核通过后自动公开”说明。
- 驳回通知和未读状态在“发布”页签上显示状态点；打开详情后标记已读。

### 20.7 审核页

- `super_admin` 的主导航在“开发”和“执行记录”之间增加“审核”，徽标显示待审核数量。
- `/reviews` 包含“待审核、审核历史、发布版本、发布设置”四个页签。
- 列表默认按提交时间从旧到新，支持工作流、提交者、分类、状态和时间筛选。
- 详情模式中央显示源码或差异，侧栏显示身份、权限、依赖、检查、审核清单和操作。
- 自审时侧栏顶部固定警告条；通过按钮先打开二次确认，并要求自审说明。
- 驳回对话框要求原因分类和详细说明；不能关闭对话框绕过必填规则。
- 审核沙箱运行状态与结果留在当前详情，不把候选加入普通工作流列表。

### 20.8 工作流页

- 现有“工作流”页面顶部增加“工作流大厅 / 已安装”页签，不新增一级导航。
- 大厅列表支持名称、描述和分类搜索，显示发布者、最新版、分类、兼容状态和权限摘要。
- 详情检查器展示发布者与署名、版本说明、权限、最低客户端版本和下载操作。
- 下载完成后切到“已安装”；更新提示由用户主动确认。
- 已撤销或不兼容状态使用不可操作行和明确说明，不只改变颜色。

### 20.9 动效、响应式与可访问性

- 只使用现有 Element Plus 与 `@element-plus/icons-vue`，不使用 Emoji 图标或新增图标体系。
- 状态刷新使用局部进度和文本，不让整页闪烁或跳回顶部。
- `prefers-reduced-motion` 延续现有全局规则。
- 低于 1180px 时决策侧栏使用现有抽屉式覆盖；代码差异保持中央区最小可读宽度。
- 所有页签、表格选择、确认框、审核清单和错误提示支持键盘与屏幕阅读器；焦点在对话框关闭后返回触发元素。

## 21. 通知、缓存与离线

- 审核通过、驳回、服务端项目构建失败、最终平台异常、正式发布完成和撤销均生成应用内通知。
- 通知存云端，用户下次登录同步；首期不发送短信或邮件。
- 本地编辑、构建、调试和运行已安装且签名有效的工作流可以离线使用。
- 提交、实时状态、审核、配置、在线大厅和下载必须联网。
- 大厅可显示最近缓存，但必须标记“离线数据”，不能发起下载。
- 客户端在启动、恢复网络和在线周期任务中同步撤销游标。

## 22. 数据保留、隐私与审计

- 已发布和已撤销版本的源码、正式产物、签名、审核与审计记录长期保留。
- 人工驳回提交的源码和构建日志默认保留 180 天，之后删除大对象，但永久保留哈希、版本、原因和审计元数据。
- 自动构建失败或上传中断对象默认保留 30 天。
- 开发者在保留期内只能查看和下载自己的历史提交材料，不能修改。
- 源码只对提交所有者和超级管理员可见；普通用户只下载正式运行包。
- 构建日志、API 错误和审计摘要执行统一脱敏，不输出 Token、私有存储签名参数、完整秘密或服务器绝对路径。
- 下载事件不保存工作流运行输入、输出、浏览内容或本地文件信息。
- 普通管理页面不提供删除审计事件的能力。

## 23. 限额与滥用防护

- 默认每账号最多 5 个活跃提交、每天最多 50 次项目构建。
- 同一工作流同一时间最多一个活跃提交。
- 项目失败后默认冷却 1 分钟；平台重试不受冷却或每日额度影响。
- 限额检查和计数更新必须在服务端事务中执行；客户端倒计时只用于体验。
- 超限错误返回公开剩余额度或恢复时间，不返回其他用户的使用信息。
- 超级管理员提交自己的工作流时也遵守构建资源限额；运维只能通过受审计策略配置调整配额。

## 24. 分阶段交付与功能开关

### 阶段 1：云端基础

完成 PostgreSQL、迁移、发布 API、CloudBase 会话验证、角色、所有权、配置、私有存储和审计。只开放测试接口，不显示桌面入口。

### 阶段 2：安全流水线

完成规范上传、隔离依赖安装、扫描、构建、候选产物、签名和发布重试。通过 API 集成测试验证状态机，仍不向普通用户开放。

### 阶段 3：开发与审核

完成开发发布页签、状态与通知、审核管理、差异查看、自审、驳回和审核沙箱。

### 阶段 4：大厅与安装

完成大厅、下载、验签、原子安装、更新、回退和撤销同步。

服务端功能开关控制发布、审核和大厅入口。只有四阶段端到端验收全部通过后，才一次性向目标环境启用；功能开关不能关闭安全门禁。

- Zip Slip、符号链接、大小写碰撞、压缩炸弹、嵌套归档和超限文件。

- 普通用户调用审核、撤销、配置和他人源码接口均被服务端拒绝。
- 自审无法跳过说明、机器门禁或审计标记。
- Builder 无数据库管理权、签名权或跨提交对象读取权。
- 日志、错误、通知和审计中没有 Token、私钥、私有对象授权或源码秘密回显。

### 25.4 UI 与回归测试

- 使用 Vue 组件测试覆盖开发发布页签、审核四页签、大厅/已安装页签、确认和错误状态。
- 使用 headless Playwright/Electron E2E 覆盖提交、驳回重提、通过发布、下载安装、升级、回退与撤销。
- 不启动可见浏览器，除非用户另行明确授权。
- 执行仓库 `typecheck`、`lint`、单元/集成测试、生产构建和打包原生依赖验证。

## 26. 风险与控制

| 风险 | 控制 |
|---|---|
| 审核源码与运行产物不一致 | 只发布服务端从冻结源码构建的产物，签名绑定哈希 |
| npm 供应链执行任意代码 | 公共源精确版本、冻结锁文件、禁脚本、禁原生、漏洞/许可证/恶意包扫描 |
| Node 内置模块绕过权限 | 只允许平台兼容层白名单，最终运行时不链接宿主 Node |
| 自审失去双人复核 | 二次确认、必填说明、独立标记和不可跳过机器门禁 |
| 并发产生重复结论或版本 | PostgreSQL 唯一约束、事务锁、状态前置条件和幂等键 |
| 发布签名步骤半失败 | 审核与发布实体分离，`publishing` 可重试且不回滚审核 |
| 撤销无法覆盖离线设备 | 明确离线边界，启动/联网/周期同步后立即禁用 |
| 动态配置削弱安全 | 只开放运营数值，安全不变量硬编码并走部署变更 |
| 源码和调试输入泄密 | 私有存储、最小可见范围、本地脱敏、服务端复扫和日志脱敏 |
| 规格跨度过大 | 四阶段交付，每阶段独立测试，完整闭环后再开放 |
